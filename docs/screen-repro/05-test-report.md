**環境上の注意(結果解釈への影響)**:
- Chromium は swiftshader(CPUソフトウェアラスタライザ)で動作しており、実機GPUと比べて1桁以上遅い。この結果、E-15(動的品質スケーリング)がテスト中に自動的に stage1〜3 へ降格する場面が頻発した。これは実装の不具合ではなく、E-15 が「フレームタイムに基づき正しく反応している」証跡として扱う(§(f)参照)。
- fps/フレーム間隔の実測値は、この理由により**参考値**であり、実機(デスクトップGPU/スマホ実機)の値を代表しない。AC-21 のfps基準そのものはヘッドレスでは判定不能なため、「計測の仕組みが正しく動作し、値が有限で取得できること」「E-15の縮退順序が仕様どおりであること」を判定対象とした。

## (f) E-15(動的品質スケーリング)降格検証

- **強制段階(`?rvq=0..4`)**: 5段階すべてで `SH._rvState.qualityLevel` が指定値と一致し(実値・複数時点で持続)、`[E-15] quality→ N` ログを確認(c-2表)。stage4のみ `viewMode="single"` かつ右ビューpassの draw call が0であることを2時点で確認し、「単一ビュー化が持続すること」(01要件のE-15除外規定・AC-1に必要な性質)を機械的に裏付けた。
- **自動降格(実測)**: マトリクステスト中、hero-G1で `ql=[1,1,1,2,2,3]`、hero-WBCで同様の推移を観測。これは `02-spec.md` §7.2 のヒステリシス(`emaMs>budget*1.25` が連続2評価窓で1段降格)がheadless swiftshader環境の低速フレームタイムに反応して正しく動作していることを示す。縮退順序は 影(stage1)→グロー/DPR(stage2)→ジオメトリ密度(stage3)→単一ビュー(stage4)の順で、`?rvq` 強制テストにおいてもこの順序に対応する段階番号が機能どおりに反映されていた。04実装ノートに記載のとおり「headless Chromiumはポインタ粗検出でモバイル級と判定され初期stage1から開始する」ため、strictにstage0からの降格開始ではなくstage1始まりだったが、これは仕様§1.4どおりの挙動であり不具合ではない。
- **フック**: `SH._rvForceQuality(4)` 実行時呼び出しで即座に `ql=4, viewMode=single` へ遷移することを確認(c-2「HOOK」行)。
