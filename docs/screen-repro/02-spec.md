- 対象モジュール: `game/js/raceview.js`(改修の主体)、`game/js/horse3d.js`(拡張)、`game/js/data.js`(定数の追加のみ、既存値は不変)。呼び出しインターフェース `SH.createRaceView(root, race, field, sim, onDone)` は変更しない。

### 記号・座標系の定義(全章共通)

| 記号 | 定義 |
|---|---|
| `D` | レース距離(m)。既存 `race.dist`(1200〜3600 等) |
| `leadM` | 先頭馬の走破距離(m)。`Math.max(...posAt(t))` |
| `R` | 残距離 = `D - leadM`(m) |
| `p` | 経過率 = `leadM / D`(0〜1) |
| `posAt(t)` | 既存の各馬走破距離配列(m)。線形補間済み |
| `course` | 既存 `makeCourse(D)`。`pos(m,lat,y)`/`heading(m)`/`at(m)`/`lap≈1653.98`/`finishFrac` |
| `TRACK_HALF` | 11(走路半幅 m)。内ラチ `lat=+11.6` / 外ラチ `lat=−11.6`、既存踏襲 |
| `lat` | 側方オフセット(m)。`course.pos` の第2引数。**正=内側(インフィールド/内ラチ側)、負=外側(スタンド側/コース外周)** と本書で統一。これは既存 `makeCourse.pos` の符号規約そのもの(既存実装: スタンド `lat=−17`、先頭馬 `targetLat=+7.5`=内ラチ寄り、クレーンカメラ `lat=+58`=インフィールド上空) |
| `VW,VH` | 1ビューの論理解像度 = 1280 × 720 |
| `DW,DH` | デュアル論理キャンバス = 2560 × 720。HUD 座標の基準系 |
| `FL` | 焦点距離(px)。FOV への換算 `fovY = 2·atan((VH/2)/FL)`。基準 830 |
| `WAKU_COLORS` | `["#ffffff","#222222","#e03131","#1c7ed6","#f5c518","#2f9e44","#f76707","#f783ac"]`(白/黒/赤/青/黄/緑/橙/桃) |
| `WAKU_TEXT` | `["#222","#fff","#fff","#fff","#222","#fff","#fff","#222"]`(白・黄・桃=黒文字、他=白文字) |

**時間基準の宣言**: 本書に現れる「秒」は特記なき限りすべて**シミュレーション秒(sim秒)**= 再生時計 `view.t` の単位である。**再生速度×N(既存 `view.speed` 既定 ×3)では実時間 = sim秒 / N**。この規約は本書の全ての秒指定 — `EMPTY_MAX`(§3.2)、L4 の先頭 2.5 秒(§3.1)、隊列チップのスライド 0.35 秒(H-3)、H-7 の保持 10 秒、自馬フレームインの 25/30 秒(§3.2)、フェード時間(§2.0)等 — に適用する。AC の秒窓(AC-10 の 8〜12 秒等)もログ上の `view.t` 差(sim秒)で判定する。参考画像の `'03…1'15` は `view.t` の表示であり、再生速度とは独立。カメラ・HUD の全スケジュールは `p` と `R` で正規化し、`view.t` に依存させない(距離・速度が変わっても様式が保たれる)。

## 1. 画面仕様

### 1.1 レイヤー構成

WebGL 経路では 2 レイヤー(WebGL + HUD)を基本とし、フォールバック経路のみ従来 3 レイヤーを使う。

| z | レイヤー | 実体 | 解像度(論理) | 役割 |
|---|---|---|---|---|
| 0 | `bgCanvas`(2D) | `<canvas>` | 2560×720 | **WebGL経路では未使用(非表示)**。フォールバック時のみ空・地面を 2D 描画(§8) |
| 1 | `glCanvas`(WebGL) | `<canvas class="layer">` | 2560×720 ×DPR | 3Dシーン本体。1フレームに左右2ビューポートを描画(§1.3)。空・地形・ラチ・馬・美術・グレアを全て内包 |
| 2 | `fgCanvas`(2D) | `<canvas class="layer">` | 2560×720 | HUD 一式(§2)。等倍(DPR非依存、テキスト鮮鋭度優先) |

- 既存 CSS(`.canvas-wrap.tv canvas.layer { position:absolute; inset:0; width:100%; height:100% }`)をそのまま流用。`bgCanvas`/`glCanvas`/`fgCanvas` の生成順・重ね順を上表に合わせる。
- キャンバスの `width`/`height` 属性を現行 1280×720 から **2560×720** へ変更(`glCanvas` は後述 DPR を乗じる)。論理サイズはコンテキストスケールで吸収し、描画コードは論理 2560×720 系で書く。

### 1.2 物理解像度と DPR(§9「物理解像度・DPR」の確定)

- **決定: 単一横長キャンバス方式(2560×720)を採用**。理由: (a) HUD が両ビューをまたぐ帯・スライド数字・分担凡例を持ち、1枚の座標系で描くのが最も単純(要件§1-B)、(b) WebGL レンダラーは 1 個で済み `renderer.setViewport/setScissor` による 2 パスでコンテキスト切替コストを避けられる。
- `glCanvas` の物理バッキングストア = `2560·q × 720·q`(`q` = 品質DPR)。`q ∈ {1.0, 0.75, 0.6, 0.5}` を E-15(§7)が制御。初期値は `Math.min(window.devicePixelRatio||1, 1.0)`(高DPR端末でも 1.0 上限=横2560で十分)。
- `fgCanvas` は常に等倍 2560×720(HUD 文字の可読性を優先)。
- CSS 表示幅はコンテナ 100%。要素比率は 2560:720 = 32:9。`.canvas-wrap` の `height:auto` で高さ追従。

### 1.3 デュアルビューのビューポート分割

- 左ビュー = `x∈[0,1280)`、右ビュー = `x∈[1280,2560)`、各 720 高。境界に 4px の暗色セパレータ(`#0a0e12`)を `fgCanvas` に描く(参考画像の 2 画面間の黒枠様式)。
- WebGL 描画(毎フレーム):
  1. `renderer.setScissorTest(true)`
  2. 左: `setViewport(0,0,1280·q,720·q)` / `setScissor(同)` → `camera.aspect=1280/720` を左カメラ解へ設定 → `render(scene,camL)`
  3. 右: `setViewport(1280·q,0,1280·q,720·q)` / `setScissor(同)` → `render(scene,camR)`
- 同一 `scene` を 2 回描画(要件§2 前提「同一シーンを1フレームに2ビューポート」)。馬の位置・ポーズ(インスタンス行列)更新はビューポート描画の**前に1回だけ**行う(§6.0・§7.1)。
- **単一ビュー縮退時(E-15 stage4)**: 左ビューのみ全幅 `setViewport(0,0,2560·q,720·q)`(aspect=2560/720)で描画し、右ビュー HUD 領域を隠す。`SH._rvState.qualityLevel=4` を記録(§7・AC-1)。

### 1.4 モバイル表示

- 目標 30fps(要件§0-5)。初期化時に `navigator.hardwareConcurrency<=4` もしくは粗いタッチ判定でモバイル級と推定し、E-15 の初期段階を stage1(影オフ)から開始してよい。
- コンテナ幅にフィット(32:9)。縦持ちスマホでは物理表示高が小さくなるため、HUD フォントは §2.2 の二層下限(第1層 28px / 第2層 18px)を死守。
- タッチ操作は既存の `fgCanvas` クリック(フェーズスキップ)を流用。マルチタッチ・ピンチは非対応(スコープ外)。

## 2. HUD 仕様(全10要素)

座標は論理 2560×720 系。フォントは総称ファミリのみ(原則 `sans-serif`、**H-8 のみ `serif`**。いずれも端末内蔵)を使用しファイル追加なし。数値は 720p 相当での実測比率に基づく。フェード曲線は特記なき限り **ease-out**(`a = 1-(1-u)²`, `u∈[0,1]`)。

### 2.0 放送HUD のフェーズ管理(§9・§3補足の確定)

- 状態変数 `hudPhase ∈ {"pre","fadein","on"}`。しきい値は **`view.t` 実測ではなく `p`(経過率)基準**で正規化し、距離不変にする。
  - `pre`: `p < P_HUD_ON`
  - `fadein`: `P_HUD_ON ≤ p < P_HUD_ON + ΔP_FADE`(進行に伴いアルファ 0→1)
  - `on`: それ以降ゴールまで
- 確定値: **`P_HUD_ON = 0.085`(発走直後の約8.5%地点でフェード開始)、`ΔP_FADE = 0.020`(=フェード区間。sim秒では `0.020·D/16` ≒ D=1200: 約1.5秒 〜 D=3600: 約4.5秒)**。
  - 根拠: 参考 #5(`'17`)で既に表示済み・#1〜#4(`'03`〜`'08`)で未表示。2000m・先頭16m/s 換算で `'08〜'17` は `p≈0.06〜0.14`。この窓の入口 0.085 を開始点とする。
  - 開始 `p=0.085` は **D≈2000m・先頭16m/s で約10.6秒(フェード完了 ≈13.1秒)= 10〜17秒に相当**し、AC-4/AC-5/AC-11 の「目安10〜17秒でフェードイン」に整合する。距離によっては 6〜19秒(D=1200: 約6.4秒 〜 D=3600: 約19.1秒)の範囲で変動するが `p` は一定。
- フェード対象 = **H-1 / H-2 / H-3(+H-4) / H-8**。非対象(発走時=`view.t≥0` から常時表示)= **H-5 / H-6**。H-7/H-9/H-10 は各自のトリガ。

### 2.1 要素別仕様

凡例: 座標は `(x,y)` 左上原点。**テキストアンカー規約(全要素共通)**: HUD 要素の指定座標は**要素(テキスト/ボックス)の左上基準**(`ctx.textBaseline="top"` 相当。`y` は上端)。右詰め要素(H-3・H-8)は `x` のみ右端基準とし、`y` は上端基準のまま。`αHUD` = §2.0 のフェードアルファ。

#### H-1 上部帯
- 位置/サイズ: `x=0, y=0, w=2560, h=60`(=画面高 8.3%、要件「7〜9%」内)。両ビュー全幅を横断。
- 背景: 芝色系の緑グラデーション(上 `#2f8f3a` → 下 `#256f2c`)にアルファ `0.82·αHUD`。下端に 3px の明線 `rgba(180,230,170,0.5)`。
- 更新: `hudPhase` に従いフェードイン。以降ゴールまで常時。毎フレーム再描画。

#### H-2 残距離数字(スライド)
- 内容: `Vshow = Math.ceil(R/100)*100` を「白抜き数字+左脇に紅白縞ポールアイコン」で表示(1700→1600→…→100→ゴール直前で消灯)。
- スタイル: フォント `bold 46px`、白 `#ffffff`、縁取り `#0c2a12` 幅 5px + 影 `rgba(0,0,0,0.4)` (オフセット2,2)。ポールアイコン = 幅7・高44 の紅白(`#e03131`/`#ffffff`)3段縞、数字左に 10px 間隔。
- **スライド則(§9 第一候補を確定)**: 「次の100m標識へ向けた線形移動+ビュー間ワープ許容」。
  - `f = (R mod 100)/100`(次の下位標識までの残り率、1→0 で標識に到達)。
  - 帯内の水平トラック `xTrack ∈ [X_L, X_R]`、`X_L=380`(左ビュー左寄り)、`X_R=1580`(右ビュー中央左)。
  - `xNum = X_R - (1 - f)·(X_R - X_L)`(f=1 で右端 `X_R`、f→0 で左へ移動)。
  - `f` が 1.0 へロールオーバー(100m通過=数字が1段減る)した瞬間、`xNum` は `X_R` へ**ワープ**(瞬間移動、補間なし)。**ビュー境界(x=1280)越え(AC-18)は、このワープではなく、`f` の減少に伴う `X_R→X_L` の連続スライドが生む**(`X_L=380 < 1280 < X_R=1580` のため、毎 100m 区間のスライドで必ず境界を横切る)。ワープは右端への復帰動作であり、境界通過の演出ではない。
  - 垂直位置 `yNum = 7`(左上アンカー基準。帯高 60 と数字高 46 の差の中央 = (60−46)/2)。
- 更新: 毎フレーム位置計算。値は `R` と ±100m 未満で一致(AC-4)。`R≤0` で非表示。

#### H-3 隊列チップ(盾形)
- 位置: 帯内右側、残距離数字と非重複の領域 `x∈[X_R+70, 2540]`(右詰め、右端から左へ並べる)。
- 表示頭数(§3補足の確定): **順位順に先頭から最大 8 頭のウィンドウ**。`n≤8` は全頭。`Nchip = Math.min(n,8)`(例: **WBC 戦は n=5 固定(§5 頭数注記)のため全 5 チップを表示**)。
- レイアウト: 右端 `x=2540` を先頭(1位)基準に、左方向へ `Nchip` 個。チップ幅 `cw`、間隔 `gap=6`。総幅が領域を超える場合 `cw` を自動縮小(`cw = clamp((2540-(X_R+70))/Nchip - gap, 30, 46)`)。高さ `chH = 38`、チップ上端 `cy = 20`(帯高60の下寄せ。帯上部 `y∈[0,20]` は H-4 自馬タグ専用ゾーンとして確保し、タグが画面上端で切れない幾何を保証する)。
- **盾形状(shield)描画仕様**(2D Canvas パス、チップ左上 `(cx,cy)`、幅 `cw`、高 `chH`、角丸 `r=6`、下部尖り深さ `tip=10`):
  ```
  moveTo(cx+r, cy)
  lineTo(cx+cw-r, cy); arcTo(cx+cw,cy, cx+cw,cy+r, r)      // 右上角丸
  lineTo(cx+cw, cy+chH-tip)                                 // 右辺
  lineTo(cx+cw/2, cy+chH)                                   // 右下→尖端
  lineTo(cx, cy+chH-tip)                                    // 尖端→左下
  lineTo(cx, cy+r); arcTo(cx,cy, cx+r,cy, r)                // 左上角丸
  closePath()
  ```
  塗り = `WAKU_COLORS[waku-1]`、外周線 `rgba(0,0,0,0.45)` 幅1.5。番号 = `bold 28px`(§2.2 第1層下限。`chH=38` に内接、尖り部を除く実質高28+パディングで成立)、色 `WAKU_TEXT[waku-1]`、中央(尖り分を避け上端から `chH*0.1` の位置に上端アンカーで配置)。
- 順位判定: 走破距離ベース(`posAt` の降順)。順位変動時、対象チップは 0.35 sim秒(ease-out)で新スロット `x` へスライド(×3再生の実時間では約0.12秒。AC-5「1秒以内」を満たす)。毎フレーム evaluate。

#### H-4 自馬タグ(隊列チップ)
- 自馬(`r.kind==="owned"`)のチップ直上、**帯上部の専用ゾーン `y∈[0,20]`**(H-3 で確保)に小ラベル(幅=チップ幅、高20、上端 `y=0`)。地 `#f76707`(橙)角丸、文字 `bold 18px #fff`(§2.2 第2層下限。高20の箱にline-height 18で内接)で現在順位(例「3」)。**タグ上端が `y=0` のためキャンバス外へ出ない(幾何保証)**。
- 自馬チップ本体を 1.15 倍拡大(高 `chH·1.15≈44`、下方向へ拡張し帯下端をわずかに越えてよい=シーン側へ突出)。順位変動に追従(タグはチップの `x` スライドに同期)。

#### H-5 出走馬凡例
- 位置: 各ビュー下部。左ビュー `x∈[24,1256]`、右ビュー `x∈[1304,2536]`。基準領域 `y∈[VH-96, VH-8]`(高 88px)、**下端 `VH-8` 固定**(上端は行数により可変、下記「行高の自動縮小規則」)。
- **左右分担規則(頭数可変で一般化)**: 全 `n` 頭を **6 列固定 × `Rrow=ceil(n/6)` 行**の行優先グリッドに敷く。セル `(row,col)` の馬番 = `row*6+col+1`(1始まり、`n` 超は空セル)。**左ビュー=列0〜2、右ビュー=列3〜5**。
  - 12頭: 左=1,2,3/7,8,9、右=4,5,6/10,11,12(参考 #5 と一致)。
  - 18頭: 3列×3行/ビュー(左=1-3/7-9/13-15、右=4-6/10-12/16-18、AC-17a)。
  - 5頭: 左=1,2,3、右=4,5(空セルは描かず崩れない、AC-17d)。**WBC 戦は §5 頭数注記のとおり常に 5 頭であり、このケースが標準適用となる**(1行グリッド)。
- **行高の自動縮小規則(18頭=3行対応)**: 行高 `rh = clamp(floor(88 / Rrow), RH_MIN, 44)`、`RH_MIN = 34`(= §2.2 第1層フォント 28px + 上下パディング 6px)。
  - 1〜2行(n≤12): `floor(88/Rrow) ≥ 44` → `rh = 44` で基準領域(高88px)に収まる。
  - **3行(13〜18頭): `floor(88/3) = 29 < RH_MIN` のため `rh = RH_MIN = 34` に頭打ちし、領域を上方拡張する**(領域高 = `rh·Rrow = 102px`、`y∈[VH-110, VH-8]`)。フォント下限(§2.2)は縮小しない — **両立は「行高の下限クランプ+領域の上方拡張」で実現**する。
  - 凡例上端 `yLegTop = VH - 8 - rh·Rrow` を公開値とし、H-6/H-7/H-8 の `y` はこれにアンカーして自動退避する(各要素の項を参照)。
- チップ: 枠色角丸(`r=4`)地 `WAKU_COLORS`、馬番 `bold 28px` 色 `WAKU_TEXT`(§2.2 第1層)、右に馬名 `bold 28px` 白+黒縁取り1.5px(第1層。セル幅超過時はフォント高を保ったまま横方向の字詰め `scaleX≥0.8`+末尾省略で吸収)。1セル = 幅約 200・高 `rh`、チップ高 `rh-6`。自馬セルは橙タグ(H-4様式)付き。
- 更新: 発走前〜ゴール後まで常時(フェード対象外)。順不同(馬番固定)。

### 3.2 右ビュー(定点カメラ列)配置と先回りロジック

右ビューは**三脚固定(揺れ0)**。コース沿いに仮想定点カメラ列を敷き、先頭が現定点を通過しきる少し前に次定点へハードカット。

- **配置間隔**: `CAM_SPACING = 200m`(要件「150〜250m」中央)。定点 `k` の設置 `m` = `Mcam(k) = k·200 + CAM_OFFSET`(`CAM_OFFSET=40`)。カメラ位置は設置 `m` に対し `pos(Mcam, latC, yC)`。
- **定点の型(巡回)**: 各定点は下記からラウンドロビンで型付け。位置/注視/FL:

| 型 | 位置 `pos(Mcam,lat,y)` | 注視 | FL | 備考 |
|---|---|---|---|---|
| R-front(正面) | `(Mcam+40, 0, 2.4)` | 先頭集団 `(leadM,0,1.6)` | 1100 | 馬群が向かってくる(#1様式) |
| R-side(側面望遠) | `(Mcam, +22, 3.2)` | 集団 `(packC,0,1.6)` | 1400(圧縮) | パン追従(位置固定・注視のみ追う、#7/#9) |
| R-diag(斜め正面) | `(Mcam+25, +16, 5.5)` | `(packC,0,1.6)` | 950 | 中団俯瞰(#12) |
| R-name(名物) | §4 の名物定点座標 | 名物構造物+通過馬 | 名物ごと | 石橋横/紅白ポール際/スタンド前(必須経由) |
| R-goal(ゴール横) | `(D-6, +14, 3.0)` | `(D,0,1.6)` | 1000 | ゴール柱を画面内(#19様式) |

- **馬群到達の機械判定**: `ARRIVE_M = 140m`。注視前方固定型(R-front/R-diag/R-goal/R-name)の定点 `k` について、**先頭が設置点の 140m 手前(`leadM ≥ Mcam(k) − ARRIVE_M`)に達した時点で「馬群到達(フレームイン)」**とみなす(FL 950〜1400 の望遠では 140m 先の馬群が判読可能サイズで映る)。
- **`camR.empty` の真偽定義(`SH._rvState.camR.empty`、AC-2 機械判定用)**:
  - 注視前方固定型(R-front/R-diag/R-goal/R-name): `empty = (leadM < Mcam(k) − ARRIVE_M)`(=馬群が定点の 140m 圏外)。
  - パン追従型(R-side。下記再同期直後の強制 R-side を含む): `empty = false`(位置固定・注視が常に馬群を捉えるため)。
- **先回り(次カメラ選択)**: 先頭が `Mcam(k) + LEAD_PASS`(`LEAD_PASS = 25m`、通過しきる直前)に達したら `k' = k+1`(=前方 200m)へカット。カット直後は馬群未到達 → **空フレーム**(空舞台)。空フレーム許容 `EMPTY_MAX = 3.5s`(sim秒、§冒頭の時間基準)。
- **空フレーム ≤ EMPTY_MAX の恒常成立(数値例)**: カット直後の先頭位置 = `Mcam(k)+25`、次定点 `Mcam(k)+200` への「到達」= 先頭が `Mcam(k)+60`(= `+200−ARRIVE_M`)に達した時。空区間の走行長 = `CAM_SPACING − LEAD_PASS − ARRIVE_M = 200 − 25 − 140 = 35m`。**先頭 16m/s で空フレーム ≈ 2.2 sim秒**、レース中の速度域(≈13〜19m/s)全体でも 1.8〜2.7 sim秒であり、**この間隔(200m)・オフセット(40m)・カット条件(25m 手前)の組で `EMPTY_MAX=3.5s` 以下が恒常成立**(成立限界は先頭 10m/s)。カット周期 = 200/16 = 12.5 sim秒 → 60 sim秒で 4〜5 カット、うち注視前方固定型のカットが「空フレーム→数秒内に馬群通過」を生む(AC-2 の「3 回以上+空フレーム 1 回以上」を満たす)。
- **再同期(セーフティネット)**: それでも `empty` が `EMPTY_MAX` を超えた場合(先頭 <10m/s の異常低速等)は、`k = ceil((leadM + 30 − CAM_OFFSET) / CAM_SPACING)` で再同期する。この式は **CAM_OFFSET を織り込み、恒等的に `Mcam(k) ≥ leadM + 30` = 必ず先頭より前方**の最寄り定点を選ぶ。同時に型を **R-side(パン追従・注視=先頭集団)へ強制**し、空フレームを打ち切る(上記定義により `empty=false`)。旧式 `k = floor((leadM−30)/200)` は先頭**後方**(通過済み)の定点を選び、直後にカット条件(a)を再満足して前後に振動するため**廃止**。
- **名物定点の強制経由**(要件 R3): 石橋区間・紅白ポール区間・スタンド区間に対応する `Mcam` は型を強制的に R-name にする(§4.2 の lap 空間配置表の各中心 `s` を当該レースの `m` へ逆写像し `Mcam` 近傍を判定、§4.2 注記)。1レースにつき各1回以上経由。**例外: `D≤1600` ではスタンド区間が優先度(e)の R-goal 固定圏(`R≤200`)に入り R-name(スタンド)は発火しないが、R-goal 自体がスタンド前定点であるため経由要件は R-goal で代替充足とみなす**。
- **自馬フレームイン保証(P1/AC-23)**: 30 秒に 1 回以上、注視を「先頭集団」から「自馬」に切替(自馬が中団以下でも)。実装: `lastOwnInView` を保持し、経過 25 sim秒で次カットを「定点 `k = ceil((leadM + 30 − CAM_OFFSET) / CAM_SPACING)`(通常の先回り位置=先頭より前方)+注視のみ自馬 `pos(ownM,0,1.6)` に固定したパン追従(R-side 扱い、`empty=false`)」とし、2.5 sim秒保持後に通常則へ復帰。前方定点のため条件(a)の即時再満足による振動はない(先頭到達まで ≥55m/16 ≈ 3.4 sim秒 > 保持 2.5 秒)。
- **カット条件まとめ**: (a)先頭が `Mcam+LEAD_PASS(=25m)` 到達、(b)空フレーム `EMPTY_MAX(=3.5s)` 超(→上記再同期+R-side 強制)、(c)自馬フレームイン要求(25 sim秒経過)、(d)名物区間侵入、(e)`R≤200` で R-goal へ固定。優先度 e>d>c>a>b。

### 3.3 両ビュー共通制約
- **同一カメラ位置の禁止**(要件§2.3): 左右のカメラ `pos` 間距離が 12m 未満かつ注視方向内積 >0.98 の場合、右ビューを次定点へ強制カット。
- **両方同時空フレームの制限**: 左が L4/L5(馬群外)かつ右が空フレームになる状況は、右の空フレーム判定で回避(左が馬群外の間は右のカットを 1 秒抑止)。
- リプレイ・掲示板は全幅1画面へ復帰(§6・既存様式)。

## 4. コース・美術仕様

### 4.1 コース幾何(既存 `makeCourse` の流用方針)

- **流用**: `makeCourse(D)`(楕円=直線450×2+半円R120×2、`lap≈1653.98`)をそのまま座標源に使う。カメラ・馬・美術の全配置に `course.pos/heading/at` を使用。
- **配置原理(物理周回座標=lap 空間基準)**: 美術オブジェクトは「レース走破距離 `m`(残距離基準)」ではなく、**物理周回座標 `s`(lap 空間、`s∈[0,1654)`。既存 `at()` 内部の弧長 `s = ((startWS + m) mod lap)` そのもの)**に沿って authoring し、ワールドへ**1回だけ静的配置**する。7 テーマは物理コース上に固定され、**全距離のレースが同一ワールドを共有**する。`D>lap` の周回(3600m 等)では**同じ景観を2回通る**(=世界として一貫。旧方式の「再訪区間に後段テーマを再配置・前段非表示化」は廃止)。表示は「カメラ近傍 ±350m の窓」のみ生成・可視化(既存 `mFrom/mTo` 方式の踏襲、視錐台カリング)。
- lap 空間の目印: `s=0` = 第1直線(ホームストレッチ)始端。決勝線は**全距離共通で `s = finishWS = 369`**(`makeCourse` の `finishWS = S·0.82 = 369`、`finishFrac = 369/lap`)。スタート `startWS = finishWS − D (mod lap)` は距離により異なる区間に落ちる(§4.2 の距離別注記)。**発走ゲートは可搬小物**として毎レース `startWS` 位置(`course.pos(0,·,·)`)に配置する(スタンド等の固定美術は動かさない)。

## 5. 照明仕様

シーンは `race` 属性で **ナイター/昼**を選択(`SH.isNightRace(race)`)。

- **ナイター選択条件(E-12 の確定)**: `race.grade === "WBC"`(参考の WBC CLASSIC がナイター様式) **または** 季節終盤の特定重賞(`race.week >= 48 && race.grade === "G1"`)。それ以外は昼。判定は `data.js` に `SH.isNightRace = function(race){ return race.grade==="WBC" || (race.week>=48 && race.grade==="G1"); }` を追加(既存値不変)。
- **頭数注記(WBC)**: `race.js` の `GRADE_BAND` で WBC は `field:[5,5]` = **5頭固定**である。したがって **WBC 戦のナイターでは HUD は 5 頭グリッドで動作する**(H-3: 全 5 チップ表示、H-5: 6列×1行グリッドの左3頭/右2頭分担 — いずれも §2.1 の H-3/H-5 に適用例を明記済み)。参考映像相当の 12 頭級(多頭数)ナイターは、本ゲームでは `week≥48 && grade==="G1"` 側の条件(G1 の field は 14〜18 頭)で発生する。

### 5.1 ナイター(基本)
- 空: 濃紺→黒の頂点グラデーション(上 `#0a0e1e` → 地平 `#1a2436`)。月(発光白円)1個 + 星少量(点スプライト 40 個程度)。
- ライト: `HemisphereLight(0x2a3550, 0x0e1a12, 0.35)`(全体を暗く)。照明塔ごとに `PointLight`(色温度 5600K 相当 `0xfff4e0`、減衰付き、走路を局所照明)を S 区間の塔位置に 4〜6 灯。走路が明るく周辺が暗い明暗差(E-10)。
- フォグ: `FogExp2(0x121a2a, 0.0016)`(遠景を夜霞へ)。
- グロー近似(E-14, ポストプロセスなし): 照明塔・月に **加算ブレンド `Sprite`**(放射状ハロ CanvasTexture、`blending=AdditiveBlending`)。右ビュー定点では画面内に光条スプライト(十字グレア)を許容(要件 R1/E-10)。
- 影: 多灯による淡いブロブ影のみ(shadowMap 不使用でも可)。

### 5.2 昼(他レース)
- 空: 既存 `skyColors(cond)` の配色を WebGL 頂点色/背景へ移植(良=青空 `#3f96de→#c2e5ff`、不良=灰 `#39424e→#67727f` 等)。雲ビルボード数個。
- ライト: `HemisphereLight` + `DirectionalLight`(太陽、既存 `buildScene` の晴/曇/雨トーンを流用)。良馬場は暖色 `0xfff2dd` 0.95、不良は寒色弱め。
- フォグ: `Fog`(遠景大気霞、既存 `hazeOf` 相当)。雨は既存 `sky.rain` の前面 2D 線を `fgCanvas` に描画。
- グロー: 昼は軽微(ハイライトのみ)。

### 5.3 区間トーン(E-11)
- 環境光(`HemisphereLight.intensity`/色)を**カメラ位置の lap 空間 `s`(§4.2 の区間)**でゆるやかに補間: 竹林 T1・森 T2・暗森 T6 は暗め(intensity ×0.8)、丘陵 T5・橋 T3 は明るめ(×1.15)。1 フレームあたり 0.02 で lerp(急変を避ける)。テーマが lap 固定のため周回(3600m)でも同一地点=同一トーンで一貫。
- 画作り(E-14): 軽いビネット(既存キャッシュ `vig` を `fgCanvas` へ流用、2560幅へ再生成)。

## 6. 馬体・アニメ仕様

`horse3d.js` を拡張(既存プロポーションを実馬比へ調整)。単位 m、ローカル +X 進行方向。

### 6.0 描画方式 — パーツ種別ごとの `THREE.InstancedMesh`(頭数非依存 draw call)

- **背景**: 現行 `createHorse` は 1 頭 ≈ **36 Mesh**(胴3・首・たてがみ・頭・鼻・耳2・目2・尾・脚 4×3・鞍・ゼッケン2・騎手9)。個別 Mesh のまま 18 頭 × 2 ビューポートを描くと馬だけで ≈1300 draw call となり §7.1 予算が破綻する。**個別 Mesh 方式は廃し、以下を正とする**。
- **方式**: 馬体・騎手の**パーツ種別ごとに `THREE.InstancedMesh` を 1 個**生成(r147 対応 API)。`count` = 頭数 × そのパーツの配置数(例: 胴球=3n、前腿=2n、下腿=4n、蹄=4n)。これにより**全馬合計の draw call = パーツ種類数 ≈ 30〜40 / パスで頭数に非依存**(5 頭でも 18 頭でも同じ)。
- **個体差は `instanceColor`(`setColorAt`)**で与える: 毛色 7 色(§6.2)、部位の陰影(下腿・鼻面の `×0.72/×0.8` 暗色はそのパーツのインスタンス色を暗くして再現)、勝負服の地色・袖色・帽色(§6.4)。マテリアルはパーツ種別ごとに**共用 1 個**(白基調、色はインスタンス色が乗る。`MeshLambert/PhongMaterial` は r147 で `instanceColor` 対応)。
- **ゼッケン番号布のみ例外**(番号テクスチャが必要なため): (i) **個別 Mesh 2 枚/頭**(18 頭で 36 Mesh)、または (ii) **番号テクスチャアトラス 1 枚**(512×512、馬番 18 タイル)+インスタンス毎 UV オフセット(`InstancedBufferAttribute`+`onBeforeCompile` の UV シフト)付き InstancedMesh(1〜2 DC)のいずれかを許容。§7.1 の予算は (i) の上限で計上する。
- **毎フレームのポーズ→インスタンス行列更新(計算方法)**: 非表示の**ポーズリグ 1 体**(既存 `createHorse` の Group 階層+`pose()` 関節計算をそのまま流用)を馬ごとに評価し、`updateWorldMatrix` 後の各パーツのワールド行列を該当 InstancedMesh の `setMatrixAt(インスタンス index)` へ書き込み、`instanceMatrix.needsUpdate = true` を立てる(≈36×18 ≒ 650 行列/フレームの CPU 合成。**2 ビューポートで共有し更新は 1 回**、§1.3・§7.1)。
- 白斑(§6.5)・勝負服の柄(§6.4)・H-9 マーカー(§2.1)の InstancedMesh 整合は各節に規定。

### 6.1 プロポーション(A-1)
- 体高(き甲まで)≈ 1.6m、体長(胸端〜臀端)≈ 2.4m、脚は細く長い。既存 `H3_SCALE=1.45` を見直し、素体を実寸で作り視認スケールは別途 `1.15` 程度に抑える(密集破綻回避)。
- 首〜胴〜臀を滑らかに: 既存の球体3分割(torso/chest/rump)を、接合部を重ねて連続シルエットにする(角張り解消、A-1)。セグメント削減は E-15 stage3 で、**共有パーツジオメトリの低セグメント版差替えとして全インスタンス一括適用**する(§6.0・§7.2。InstancedMesh 化によりジオメトリは全馬共有のため差替えは種別数 ≈40 回で済む)。

### 6.2 毛色・ツヤ(A-2)
- 既存 7 毛色(`COAT`: 鹿毛/黒鹿毛/栗毛/栃栗毛/芦毛/青毛/白毛)を継承。**毛色はマテリアル色ではなく `instanceColor`(`setColorAt`)で馬ごとに与える**(§6.0)。マテリアルはパーツ種別ごとに共用 1 個の白基調とし、`MeshLambertMaterial` → 軽い `MeshPhongMaterial`(低 `shininess≈18`、`specular` 弱)へ変更しツヤ付与。E-15 stage3 で Lambert へ戻す(差替えは共用マテリアル ≈40 個のみ)。

### 6.3 ゼッケン(A-4)
- **青地に白の馬番**(現行の白地黒数字 `numTexture` を改修): 128×128、地 `#1c4f9e`(青)、白縁、白数字 `bold 74px #fff`、下部に小さな飾り文字列(判読不能の様式、実在表記の複製をしない)。両側面(既存 `cloth` ×2)に表示。
- 描画形態は §6.0 の例外規定に従う: **個別 Mesh 2 枚/頭**(テクスチャ 128×128 × n)**または番号アトラス 1 枚**(512×512、18 タイル)+UV オフセット付き InstancedMesh。

### 6.4 勝負服バリエーション生成規則(A-5)
- 枠色に限定せず馬ごとに多彩化。決定的生成(同一馬=同一服): シード `seed = r.gate*2654435761 ^ hash(r.name)`。
  - 地色 `base` = パレット12色から `seed%12`。
  - 柄 `pattern ∈ {無地, 縦縞, 袖違い, 一本襷, 星散}` = `(seed>>4)%5`。
  - 帽子色 `cap` = **`WAKU_COLORS[r.waku-1]`(枠帽子は枠色=実際の競馬様式を踏襲)**。
  - 袖 `sleeve` = `base` の明暗変化 or 別パレット色。
- 実現方法(§6.0 の InstancedMesh 整合): 地色・袖色・帽色は**胴・袖・帽を別パーツ種別とし各 `instanceColor` で個体差**(追加 draw call なし)。柄(縦縞/一本襷/星散)は**共有柄アトラス 1 枚**(256×256、柄タイル=白線画の乗算合成)+インスタンス毎 UV オフセット(ゼッケンアトラスと同じ機構)で胴パーツに付与し、個体別テクスチャ・個体別マテリアルは作らない。ヘルメット・ゴーグルは既存騎手メッシュ(のパーツ種別)を継承。

### 6.5 顔白斑(A-3)
- 確率的・決定的付与: `seed` から `blaze ∈ {なし, 星(額の小円), 流星(鼻筋の縦帯), 鼻白(鼻端の白)}`。同一馬は常に同一(seed 固定)。
- 実装(§6.0 の InstancedMesh 整合): 白斑は**小型白メッシュ 3 種(星=小円板/流星=細帯/鼻白=キャップ)の専用 InstancedMesh**(+3 DC/パス)とし、該当しない馬・種はスケール 0 行列で非表示。旧案の「毛色マテリアルへの CanvasTexture 乗算」は個体別マテリアルを要し instancing と両立しないため廃止。出走馬の 40〜60% に付与(AC-22 で確認できる程度)。

### 6.6 襲歩サイクル(A-6)
- 既存 `pose(phase, running)` を踏襲・強化。4拍ギャロップ:後肢(HL→HR)接地→前肢(FL→FR)接地、位相オフセット(HL:0, HR:+0.45, FL:π+0.35, FR:π+0.8)。
- **懸垂期**(4脚が地を離れる、A-6): `root.position.y` の上下動サイクルに、全脚が引き上がる位相窓(`sin(phase*0.5+φ)` のピーク付近で全脚 `knee` を屈曲)を設ける。ストライド周期は速度連動: `phase += v·dt·k`(`v`=各馬速度、既存は `m/3.4` の擬似連動 → 実速度 `sim.frames[].v` へ接続)。
- セカンダリ: 首の前後スイング、たてがみ・尾の揺れ(既存 tailPivot/neckPivot を継承)。

### 6.7 騎手モーション(A-7)
- 前傾騎乗(既存)。終盤(`R<400`)で「追う」動作: 腕・上体の周期プッシュ(`jockey.rotation` に `sin(phase)` プッシュ加算)。ゴール後(`sim.times[i]<t`)は立ち上がり流す(前傾角を緩める)。

### 6.8 群れの隊列力学(A-9)
- 横位置 `lat` は順位で内外へ配分(既存: `targetLat[hi] = 7.5 - 15·rank/(n-1)`)を継承しつつ、密集時の相互めり込み最小化のため近接反発(同 `m` 帯で `lat` 差 < 1.2m の馬同士を微小に押し分ける)を追加。Z-fighting 回避のため各馬 `m` に微小オフセット(`i·0.02m`)。最大18頭で破綻しない(AC-20)。内外の出し入れ(順位変動で `lat` が lerp)。

### 6.9 モーションブラー近似(A-8)
- 方式(いずれか併用、右ビュー側面クローズ/流し撮り時に発動):
  - (a) **背景水平流し**: 側面クローズ(L6/R-side)で、遠景ビルボードに進行方向逆向きの残像(半透明複製を 2〜3 枚オフセット描画)。
  - (b) **地面テクスチャ流し**: 走路テクスチャ UV を毎フレーム進行方向へスクロールし放射ブラー感(参考 #1 の放射状ブラー)。
  - (c) **脚部残像スプライト**: 高速時、脚下に半透明の掃引スプライト。
- AC-19 補助基準(背景が進行方向逆向きに流れる)を (a)/(b) のいずれかで満たす。

### 6.10 フォールバック(A-10)
- WebGL 不可時は既存スプライト馬(`spriteSide/spriteFront/spriteRear`)で全ショットを近似(§8)。

| 指標 | 予算 | 手段 |
|---|---|---|
| draw call | **≤ 280 / フレーム(2パス合計。1パスあたり ≤ 140)** | 内訳(1パス): 馬体+騎手 = パーツ種別 InstancedMesh **≈40(頭数非依存**、§6.0。白斑3種含む**)** / ゼッケン個別 Mesh ≤36(18頭時。アトラス方式なら 2)/ コース・美術 ≤50(ラチ・生垣・柵・竹・観客を区間ごとに `BufferGeometry` マージ+`InstancedMesh`)/ 空・月星・グレア・H-9 マーカー ≤12 / ブロブ影(インスタンス化)≈2。**280 DC/フレームはデスクトップ GPU の 60fps 維持余裕域であり stage0 が実際に恒常維持できる**(ゼッケン・アトラス採用時は ≤210/フレーム) |
| 三角形 | ≤ 350k / フレーム | 遠景ビルボード化、カメラ近傍 ±350m 窓カリング、LOD(instancing は三角形数を変えないため従来どおり) |
| テクスチャ | ≤ 24 枚、各 ≤ 512×512、VRAM < 48MB | 全 CanvasTexture キャッシュ、区間で共用。ゼッケン/柄はアトラスで共有(§6.0・§6.4) |
| 描画オブジェクト | ≤ 150 / ビューポート(InstancedMesh は 1 と数える) | 視錐台+距離カリング |
| 馬 | 最大18頭。**全馬合計 ≈40 InstancedMesh + ゼッケン(個別方式時 2 Mesh/頭)** — 頭数を増やしても draw call は増えない | ポーズはリグ 1 体を n 回評価し `setMatrixAt` で行列書込み(§6.0)、更新は毎フレーム 1 回、描画は 2 パスで共有 |

- フレーム構造: 「(1)シム位置更新→(2)左右カメラ解算→(3)ポーズリグ評価+全 InstancedMesh 行列書込み(1回、§6.0)→(4)左viewport描画→(5)右viewport描画→(6)HUD描画」。(3)を2回描画で共有しCPU負荷を半減。

### 7.2 E-15 動的品質スケーリング(P0)

- **計測**: `rAF` 間隔の指数移動平均 `emaMs`(係数 0.1)。評価は 30 フレームごと。基準フレーム予算 `budget` = 16.7ms(PC)/33.3ms(モバイル、§1.4 判定)。
- **降格/昇格(ヒステリシス)**: `emaMs > budget·1.25` が連続2評価窓 → 1段降格。`emaMs < budget·0.7` が連続4評価窓 → 1段昇格。発動・段階をログ出力(`console.info("[E-15] quality→", level)`)し `SH._rvState.qualityLevel` に記録(AC-21)。

| stage(qualityLevel) | 無効化/縮退する機能 | DPR(q) |
|---|---|---|
| 0(full) | なし(影・グロー・全密度・デュアル) | 1.0 |
| 1 | **影**を無効(shadowMap off、ブロブ影のみ) | 1.0 |
| 2 | **グロー/ハロ/光条スプライト**を無効、フォグ簡略 | 0.75 |
| 3 | **ジオメトリ密度**削減(観客数半減・竹/木ビルボード間引き・馬パーツ共有ジオメトリを低セグメント版へ一括差替え(§6.0)・生垣インスタンス半減・Phong→Lambert(共用マテリアル差替えのみ、§6.2)) | 0.6 |
| 4(最終手段) | **単一ビュー化**(右ビューポート停止、左のみ全幅)。`qualityLevel=4` を記録(§1.3・AC-1) | 0.5 |

- 縮退順序 = 影→グロー→ジオメトリ密度→単一ビュー(要件 E-15 規定どおり、AC-21 で検証)。

## 8. フォールバック仕様(WebGL 不可)

- **判定**: 既存 `SH.Horse3D.available()`(`typeof THREE`)かつ `createRenderer` が非 null(`try/catch` で WebGL コンテキスト取得可)。いずれか失敗で `use3d=false`。加えて明示無効フラグ `SH._forceNoWebGL`(テスト用、AC-16)で強制フォールバック可。
- **動作**: `use3d=false` の場合、
  - デュアルビューを断念し**既存の単一ビュー番組構成**(2D スプライトレンダラー、1280×720 全幅)で完走(要件 P-8)。キャンバスは 1280×720 に戻す。
  - HUD は縮退版: **H-2(残距離)・H-6(経過タイム)・H-8(レース名)相当**を単一ビューに表示(P-8)。H-1帯・H-3隊列チップは既存 2D 版(現行 `drawOverlay` の隊列チップ・コースマップ)を流用。
  - 馬は `spriteSide/spriteFront/spriteRear`。カメラは既存 `computeCam`(gate/track/crane/stretch/goal)。
  - `SH._rvState.viewMode="single"`、`qualityLevel` は無効(WebGL非経路)だが `null` を設定。
- コンソールエラー0で完走(AC-16)。既存ゲームフロー(馬券→観戦→リプレイ→掲示板→払戻)は無退行(AC-15)。
